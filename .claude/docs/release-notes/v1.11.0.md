## Phase C — Memory + SOW integration

### C1 — `CLAUDE.md` per-project memory template

New file: `skills/_spine/shared-knowledge/claude-md-template.md`.

Per-project memory file Claude Code auto-loads at session start. Contains:
- Project identity (client, platform, type, plan, launch date)
- SOW + Spec references (paths)
- Team
- Current gate state + gate completion log
- Recent decisions (last 5-10, one line each)
- Open blockers
- Required-from-client status
- Design tool lock (D-DES-01)
- Platform config (theme baseline, repo, hosting, staging URL)
- Apps/plugins installed
- Active tasks this sprint
- Session log pointer

Hard cap: 300 lines. Older content goes to `docs/decision-log.md` and `docs/handoff-log-<date>.md`.

### C2 — Session handoff protocol updated

`skills/_spine/shared-knowledge/session-handoff-protocol.md` — new load order at session start:

1. `check-env.sh`
2. Read `CLAUDE.md` at project root (universal context)
3. Read `outputs/<client_slug>/sow-spec.md` if present (intake + FLAG-004 + design lock)
4. Read `HANDOFF.md` at project root if present (last session's working state)
5. Cascade-load platform + project-type skills based on CLAUDE.md
6. Surface to developer with platform + gate + last task + queued tasks summary

### C3 — PM Agent SOW-aware (the value unlock)

`skills/_spine/pm-agent/knowledge/13-g0-intake-gate.md` — new Step 0 section.

PM Agent now reads `outputs/<client_slug>/sow-spec.md` BEFORE running the intake interview. If the spec exists:

- 28 frontmatter fields are pre-filled (platform, project type, launch date, design tool, FLAG-004 blocklist, modules, scope, etc.)
- The interview drops from 100+ questions to ~6 outstanding items (hosting confirmation, repo URL, credentials protocol, app versions, brand asset locations, third-party integrations)
- Validation runs on the spec before trusting it (design.tool must be HTML, FLAG-004 blocklist must have ≥ 1 email, internal_pm_email must be @webdesksolution.ca, etc.)
- Audit trail logged to `intake/spec-ingestion.log`

If no spec is present, PM Agent falls back to the legacy 100+ question interview.

**This is the entire reason the SOW Builder was built.** Without C3, the SOW Builder agent's output is dead-end. With C3, sales team → PM Agent has a structured handoff.

## How to install + use

See `docs/user-guide/SETUP-INSTRUCTIONS.md`. Same install process as v1.10.0.

### Running the frontmatter validator

```bash
cd webdesk-ai-delivery-system
python3 tools/scripts/validate-frontmatter.py skills/
# or
tools/scripts/validate-frontmatter.sh skills/
```

Add to CI: validate every PR before merge.

### Starting a new project — workflow with SOW Builder + v1.11.0

1. **Sales person** runs SOW Builder agent on the validation spreadsheet. Produces:
   - `sow-client.md` (signing doc, sent to client)
   - `sow-spec.md` (AI-facing spec, fed to PM Agent)

2. **Internal PM** creates the project repo. Copies `sow-spec.md` to `outputs/<client_slug>/`.

3. **Internal PM** initializes `CLAUDE.md` at repo root using the template (`_spine/shared-knowledge/claude-md-template.md`).

4. **Developer** opens Claude Code in the project root. CLAUDE.md auto-loads.

5. **PM Agent at G0**: Step 0 ingests sow-spec.md. Pre-fills ~85% of intake. Asks the ~6 outstanding questions. Proceeds to G0.5 audit.

6. Subsequent gates G1 through G6 proceed as before.

## Honest notes

1. **Phase B description backfill was opportunistic.** I extracted descriptions from each KB file's blockquote where possible. Some are excellent ("WordPress PHP coding standards: nonces, sanitization, escaping, capability checks"); some are vague ("Per global rules in forbidden-global.md..."). Cleanup pass in v1.12.0 will improve the vague ones. The validator allows them today.

2. **The `tools:` whitelists are CONSERVATIVE.** I gave most agents Read/Write/Edit/Glob/Grep/Bash. That's not actually a restriction — it's a baseline. Tighten over time as we see which agents actually need Write vs read-only.

3. **`name` validator rule was relaxed mid-build** to accept `{platform}-{project-type}` patterns (e.g., `name: shopify-redesign` for directory `redesign`). The directory uniqueness comes from the parent path, so the skill name including the platform is fine. Documented in the validator code.

4. **CLAUDE.md template hasn't been pilot-tested.** First real test will be the next pilot project. Expect 2-3 fields to need adjustment.

5. **PM Agent SOW-aware change is critical but unverified.** Until a real SOW spec file flows through PM Agent at G0, we don't know if the 6 outstanding questions cover everything. Could be that we need 10 instead of 6. Will know after first pilot using both Sales Agent + PM Agent.

6. **Pilot 2 (WordPress Version Upgrade) is in another window.** v1.11.0 changes do NOT affect Pilot 2's current state — it can finish on v1.10.0. New pilots after v1.11.0 ships will use the new flow.
