## What ratified — D-KB-FIDELITY-01

**Spine-level, universal.** KB content authored against a ratified D-code MUST match the ratified proposal in `_decisions/proposals/{arm}/`. Specifically:

- **Verbatim rules stay verbatim.** No paraphrase, no shortening, no summarization.
- **Numbered lists stay in order and count.** Review points, check IDs, qualification questions, anti-patterns.
- **IDs stay stable.** `B3` in the decision means the same thing as `B3` in the KB.
- **Halt responses stay in count.** Removing a documented response makes the gate falsely strict.
- **Open questions stay marked open.** Answering master's open question locally is a decision-authority failure.

**The rule is NOT "match the summary in the inventory."** Inventory summaries deliberately abbreviate. The proposal is authoritative for numbered/named content.

**Enforcement:** each arm's hallucination-guard CRITICAL code extended to cover ratified decision content, not just verified facts. Shopify: `SHOPIFY-HALLUCINATION-01`. WP: `WP-HOOK-HALLUCINATION-01`. Headless: `HEADLESS-HALLUCINATION-01`. Same discipline the Headless window already applied to API facts + numbers, now covering decision content too.

**Validator does not currently enforce this.** Tooling to diff KB content against `_decisions/proposals/{arm}/` is a v1.12.x follow-up. Until then, the discipline is: KB author reads the proposal, diffs their draft against it, cites the proposal path in the file header.

Full text in `_decisions/decision-inventory.md` under D — Agents & Core Architecture.

## Packaging bug — `__pycache__` bytecode excluded

The Headless window found `webdesk-headless-v1.11.19.zip` shipping `tools/scripts/__pycache__/validate-frontmatter.cpython-310.pyc` — a stale compiled copy of the script that changed the same release (the glob fix). Generated when the validator ran during the ship gate, then packaged.

Two problems: (a) stale bytecode is a maintenance-liability class of artifact, and (b) `__pycache__` regenerates on every validator run, so it's **noise in any content hash computed over `tools/`** — the same content-hash check that produced its first real catch in v1.11.18.

**Fix:** `-x '*__pycache__*' -x '*.pyc'` added to the zip step in the packaging shell function. Verified: v1.11.20 headless bundle has 0 `__pycache__`/`.pyc` entries.

Same family as the two silent-exit bugs from v1.11.16 and v1.11.18: an artifact the pipeline didn't expect to be there. Adding pre-package artifact sanity to my checklist.
