## What ratified

### D-HL-STACK-01 (rev 4)

Four architectures — **A** Hydrogen + Oxygen, **B** Hydrogen + self-host, **C** Shopify Headless channel + Next.js App Router, **D** BigCommerce Catalyst + self-host — with three-mode selection protocol (DECLARED / DERIVED / BLOCKED) and hosting-ownership default (client owns account, WebDesk deploys; managed service is priced add-on; declined = explicitly OUT).

**Architecture C demoted to SUPPORTED-ON-DEMAND** — the same consistency test that promoted B from SUPPORTED-ON-DEMAND to full support (named client requirement) applied to C. There is no named client for C. C's presumptive framework (Next.js App Router) is recorded but full KB defers until a client requires it. Build order: **A → B → D** (C deferred).

Rejected candidates listed with rationale (Vue/Nuxt, Remix standalone, Saleor/Vendure/Medusa, custom composable, Hyvä — belongs in the Magento arm, not headless).

### D-HL-TYPES-01 (rev 3)

Five project types (New Build, Replatform, Migrate-to-Headless, Redesign, Framework Upgrade) plus one ongoing engagement type (**Headless Support / Retainer**). Discriminator: which layer is changing.

**Data migration is owned by separate WebDesk migration skills**, not this arm. Headless arm owns: (1) the existing-site audit, (2) the handoff interface (named entity list + URL inventory + credential-reset consequence), (3) frontend consequences (redirect implementation, login/reset UX).

**Retainer defaults ratified:** 8-hour per-ticket threshold above which becomes a change order; no response-time SLA (matches declined-hosting-management posture). Both reviewed after 10 real retainer engagements against actual ticket distribution.

### D-HL-DISCOVERY-01 (rev 3)

Mandatory seven-point compatibility audit before SOW pricing on every headless project type except New Build. Binding rule preserved verbatim (never assume theme feature/app compatibility carries over). Multipass documented as a build path split into discovery-half (build now) and implementation-half (deferred until named Plus client). Discovery findings that belong to another skill (data migration, credential handling) name the handoff and the confirmation needed back — an unhanded-over finding is this arm's gate failure, not the other skill's.

The Headless window explicitly called this the **highest-leverage code in the packet**: every other headless failure mode is a discovery failure that reached build. Master agrees.

### D-HL-APPS-01 (rev 2)

Four-bucket app classification with named evidence per bucket: (1) Fully compatible, (2) Custom integration required, (3) Replacement required, (4) Requires discovery. Default bucket is 4 (undetermined). Five-question qualification gate per app.

Skill owns the classification policy, qualification gate, evidence standard, and commercial consequence. **Developer owns wiring per app** — app-by-app integration instructions are stale within one quarter and there are thousands of apps; this is deliberate scope discipline.

**Cross-engagement app-classification register: heuristic-only with 90-day per-entry expiry, never authoritative.** Master's Q4 ruling. Treating shared data as ratified truth would recreate the "assumed to work" bug D-HL-DISCOVERY-01 is trying to prevent. Register schema drafted when second engagement lands (bootstrap value = 0 until then).

### D-HL-SEC-01 (rev 2)

Headless security baseline. Ship gate blocks release. Token classification table (Storefront public / private / Customer Account API client secret / Admin API / Multipass / BigCommerce Store API / webhook signing) with browser-accessibility + storage location per token. Test that resolves every argument: *"If this repository were public on GitHub tomorrow, what could an attacker do?"*

**Mandatory SOW boilerplate ratified** for every B/C/D SOW including the declined-management case:

> *"Client owns hosting, monitoring and incident response. WebDesk responds on request at prevailing hourly rates, no response-time commitment."*

This is master's Q3 ruling. Silence here is what turns the first outage into a free-work argument.

Env-variable discipline flagged: framework-prefix conventions (`VITE_`, `NEXT_PUBLIC_`) — accidental public prefix on a secret publishes it silently at build time.

Server-layer rate limiting per D-HL-SEC-01 §7 acknowledges the BigCommerce shared-quota blast radius: all apps on a store share the quota; an unthrottled proxy route takes down every other app on the store, not just the storefront.

### D-HL-ENV-01 (rev 2)

Environment preflight. **No headless build starts until preflight has run and been recorded.** Failed preflight halts (does not become a backlog ticket) and carries **D-QA-GATE-BLOCK semantics** (master's Q5 ruling).

Nine universal checks + per-architecture checks. Two critical items:

- **Check 1**: Node version from `engines`, not from docs. Shopify's own getting-started page says Node.js v16.20+; the actual CLI package declares `engines: { node: '^22 || ^24' }`. Node 16 was EOL September 2023. Following the docs gets an environment that can't install the toolchain.
- **Check B1**: For architecture B (Hydrogen + self-host), a deploy spike on the actual target host is required **before signature** — not before build. Shopify's self-hosting guide is documented as possibly a year stale (warning: *"might not be compatible with features introduced in Hydrogen version 2025-05 and above"* while current Hydrogen is 2026.4.4). Nobody signs a fixed price against instructions Shopify has flagged as stale.

Vendor APIs move fast; 90-day expiry balances leverage against staleness; every entry gets re-verified before entering a fresh SOW.
